1 Purpose of this stage

This notebook opens Phase 2 of the project and is Stage 4 of the pipeline. It picks up directly from Stage 1.5’s preprocessed splits (*_prep.csv.gz) and does two things, in order:

  1. Feature engineering — a small number of new, economically-motivated features built from columns Stage 1 already produced (interactions, ratios, a log-price term, and two frozen-breakpoint bins). No new external data is introduced; nothing here uses a row’s own outcome or any future-period information.
  2. Feature selection — a filter → embedded pipeline (near-zero-variance, pairwise correlation, Variance Inflation Factor, LASSO, and Random-Forest importance) that decides, with evidence, which features earn a place in the Stage 6 model zoo.

Everything here is fit only on model_train and applied unchanged to every other split — the same discipline Stage 1.5 established for medians, category levels, and normalization parameters.

Decision carried over from Stage 3, formalized here: value_exposure is the CRC policy loss weight, not a classifier input (project report, §5). It is excluded from every candidate feature list from the start and carried through as a pass-through column only.

Decision carried over from Stage 3, generalized here: type_median_price was exactly collinear with productType’s dummies for linear models. Rather than drop it globally, this stage produces two feature lists — linear_features (VIF-screened) and tree_features (keeps collinear-but-informative features, since trees handle collinearity natively).

1.1 This revision’s two fixes

(a) A real duplicate-memory bug, not just a naming choice. The previous draft used list2env() to flatten the engineered splits back into globals named model_train/validation/etc., while the raw, pre-engineering objects stayed around under their original *_prep names — two full copies of the same table, simultaneously, for no reason. This revision keeps exactly one name per split in memory at any time: model_train throughout, with the other four splits never all loaded together (see “Memory profile” below).

(b) product_customer_risk_gap is exactly collinear with features already in the candidate pool — it is defined as productReturnRate − customerReturnRate, and both of those remain candidates in their own right. This is mechanically the same disease as Stage 3’s type_median_price/productType alias. The VIF step below (now a plain, dependency-free 1/(1-R^2) calculation) catches this automatically: a feature that is an exact linear combination of others gets VIF = Inf and is dropped first, with no separate alias pre-check needed.

1.2 Memory profile (6 GB RAM)

This stage is written to run inside a tight RAM budget. Concretely:

  • Only one split is ever fully loaded at once. Phase A fits engineering/binning/selection on model_train alone; Phase B re-reads, transforms, and writes each of the five splits one at a time, calling rm() + gc() between each. future_test (1.46M rows) is never loaded until every other split has already been written and freed.
  • No car dependency. car::vif()’s install chain (lme4 → quantreg → Matrix/RcppEigen) is exactly what broke the R 4.2.2 install earlier in this project. VIF is recomputed here as a direct 1/(1-R^2) regression — six lines, zero extra dependencies, and mathematically identical for a model with only continuous predictors (which is all the VIF step ever used it for).
  • Capped, documented subsamples for the two heaviest fits: cv.glmnet (100k rows, 3-fold, not 250k/5-fold) and ranger (100k rows, 150 trees, write.forest = FALSE since only $variable.importance is needed — this alone avoids storing 150 full tree structures in memory).
  • Explicit gc() after each heavy fit and before Phase B begins.

If you still run out of memory after this, the next lever to pull is shrinking LASSO_SAMPLE_N/RF_SAMPLE_N further (e.g. to 50,000) — tell me the exact error and I’ll adjust.

# fwrite()/fread() round-tripping doesn't preserve factor type (same note as
# Stage 3) -- restore it with the exact training-time level set.
restore_factor_types <- function(dt, preproc) {
  for (col in names(preproc$allowed_levels)) {
    if (col %in% names(dt)) {
      levs <- union(preproc$allowed_levels[[col]], "OTHER")
      set(dt, j = col, value = factor(dt[[col]], levels = levs))
    }
  }
  dt
}

# Pure functions used in both Phase A (fitting) and Phase B (applying to
# every split) -- defined once here so the two phases can never drift apart.
add_engineered_features <- function(dt) {
  # price_discount_interaction: is a heavily-discounted item priced far from
  # what's typical for its type?
  dt[, price_discount_interaction := price_to_type_median * discount_ratio]
  # customer_value_at_risk: expected cost-weighted historical
  # return-proneness of this customer. NOT leakage: customerReturnRate is
  # Stage 1's pre-computed historical aggregate, value_exposure is
  # price-derived -- neither uses this row's own outcome.
  dt[, customer_value_at_risk := value_exposure * customerReturnRate]
  # product_customer_risk_gap: does this product return far more/less than
  # this customer typically does? NOTE: this is *why* it later shows up
  # with VIF = Inf -- it is an exact linear combination of
  # productReturnRate and customerReturnRate, both of which remain
  # candidates in their own right. It is expected to be dropped from
  # linear_features by the VIF step, and that is the correct, intended
  # behavior, not a bug to chase.
  dt[, product_customer_risk_gap := productReturnRate - customerReturnRate]
  # log_price: raw price on a log scale (log_sales/log_returns already
  # existed; the price level itself did not).
  dt[, log_price := log1p(avgGbpPrice)]
  # male_premier: interaction of the two binary customer attributes.
  dt[, male_premier := isMale * premier]
  dt
}

4.4 Step 3 — Variance Inflation Factor (VIF), linear-model view only, no car dependency

A plain 1/(1-R^2) VIF: regress each candidate feature on every other candidate feature and read off R². This is mathematically identical to car::vif() for a model with only continuous predictors (which is all this step ever needed), and avoids car’s heavy, R-version-sensitive dependency chain entirely. Computed on a capped subsample purely to keep each iteration’s lm() call cheap – VIF is a property of the predictor correlation structure, not something that needs the full 890k rows to estimate stably.

Code 
manual_vif <- function(data, features) {
  sapply(features, function(f) {
    others <- setdiff(features, f)
    if (length(others) == 0) return(1)
    probe <- lm(as.formula(paste(f, "~", paste(others, collapse = " + "))), data = data)
    r2 <- summary(probe)$r.squared
    # r2 essentially 1 means f is an exact (or near-exact) linear combination
    # of the others -- e.g. product_customer_risk_gap vs.
    # productReturnRate/customerReturnRate. VIF = Inf is the correct,
    # expected signal here; the loop below removes it first automatically.
    if (r2 >= 0.999999) return(Inf)
    1 / (1 - r2)
  })
}

# Purpose of this stage

This notebook opens **Phase 2** of the project and is **Stage 4** of the pipeline. It picks up directly from Stage 1.5's preprocessed splits (`*_prep.csv.gz`) and does two things, in order:

1.  **Feature engineering** — a small number of new, economically-motivated features built from columns Stage 1 already produced (interactions, ratios, a log-price term, and two frozen-breakpoint bins). No new external data is introduced; nothing here uses a row's own outcome or any future-period information.
2.  **Feature selection** — a filter → embedded pipeline (near-zero-variance, pairwise correlation, Variance Inflation Factor, LASSO, and Random-Forest importance) that decides, with evidence, which features earn a place in the Stage 6 model zoo.

Everything here is fit **only on `model_train`** and applied unchanged to every other split — the same discipline Stage 1.5 established for medians, category levels, and normalization parameters.

**Decision carried over from Stage 3, formalized here:** `value_exposure` is the CRC **policy loss weight**, not a classifier input (project report, §5). It is excluded from every candidate feature list from the start and carried through as a pass-through column only.

**Decision carried over from Stage 3, generalized here:** `type_median_price` was exactly collinear with `productType`'s dummies for linear models. Rather than drop it globally, this stage produces **two** feature lists — `linear_features` (VIF-screened) and `tree_features` (keeps collinear-but-informative features, since trees handle collinearity natively).

## This revision's two fixes

**(a) A real duplicate-memory bug, not just a naming choice.** The previous draft used `list2env()` to flatten the engineered splits back into globals named `model_train`/`validation`/etc., while the raw, pre-engineering objects stayed around under their original `*_prep` names — two full copies of the same table, simultaneously, for no reason. This revision keeps exactly **one** name per split in memory at any time: `model_train` throughout, with the other four splits never all loaded together (see "Memory profile" below).

**(b) `product_customer_risk_gap` is exactly collinear with features already in the candidate pool** — it is defined as `productReturnRate − customerReturnRate`, and both of those remain candidates in their own right. This is mechanically the same disease as Stage 3's `type_median_price`/`productType` alias. The VIF step below (now a plain, dependency-free `1/(1-R^2)` calculation) catches this automatically: a feature that is an exact linear combination of others gets VIF = `Inf` and is dropped first, with no separate alias pre-check needed.

## Memory profile (6 GB RAM)

This stage is written to run inside a tight RAM budget. Concretely:

- **Only one split is ever fully loaded at once.** Phase A fits engineering/binning/selection on `model_train` alone; Phase B re-reads, transforms, and writes each of the five splits **one at a time**, calling `rm()` + `gc()` between each. `future_test` (1.46M rows) is never loaded until every other split has already been written and freed.
- **No `car` dependency.** `car::vif()`'s install chain (`lme4` → `quantreg` → `Matrix`/`RcppEigen`) is exactly what broke the R 4.2.2 install earlier in this project. VIF is recomputed here as a direct `1/(1-R^2)` regression — six lines, zero extra dependencies, and mathematically identical for a model with only continuous predictors (which is all the VIF step ever used it for).
- **Capped, documented subsamples** for the two heaviest fits: `cv.glmnet` (100k rows, 3-fold, not 250k/5-fold) and `ranger` (100k rows, 150 trees, `write.forest = FALSE` since only `$variable.importance` is needed — this alone avoids storing 150 full tree structures in memory).
- **Explicit `gc()`** after each heavy fit and before Phase B begins.

If you still run out of memory after this, the next lever to pull is shrinking `LASSO_SAMPLE_N`/`RF_SAMPLE_N` further (e.g. to 50,000) — tell me the exact error and I'll adjust.

restore_factor_types <- function(dt, preproc) {
  for (col in names(preproc$allowed_levels)) {
    if (col %in% names(dt)) {
      levs <- union(preproc$allowed_levels[[col]], "OTHER")
      set(dt, j = col, value = factor(dt[[col]], levels = levs))
    }
  }
  dt

# Pure functions used in both Phase A (fitting) and Phase B (applying to
# every split) -- defined once here so the two phases can never drift apart.
add_engineered_features <- function(dt) {
  # price_discount_interaction: is a heavily-discounted item priced far from
  # what's typical for its type?
  dt[, price_discount_interaction := price_to_type_median * discount_ratio]
  # customer_value_at_risk: expected cost-weighted historical
  # return-proneness of this customer. NOT leakage: customerReturnRate is
  # Stage 1's pre-computed historical aggregate, value_exposure is
  # price-derived -- neither uses this row's own outcome.
  dt[, customer_value_at_risk := value_exposure * customerReturnRate]
  # product_customer_risk_gap: does this product return far more/less than
  # this customer typically does? NOTE: this is *why* it later shows up
  # with VIF = Inf -- it is an exact linear combination of
  # productReturnRate and customerReturnRate, both of which remain
  # candidates in their own right. It is expected to be dropped from
  # linear_features by the VIF step, and that is the correct, intended
  # behavior, not a bug to chase.
  dt[, product_customer_risk_gap := productReturnRate - customerReturnRate]
  # log_price: raw price on a log scale (log_sales/log_returns already
  # existed; the price level itself did not).
  dt[, log_price := log1p(avgGbpPrice)]
  # male_premier: interaction of the two binary customer attributes.
  dt[, male_premier := isMale * premier]
  dt
}

## Step 3 — Variance Inflation Factor (VIF), linear-model view only, no `car` dependency

A plain `1/(1-R^2)` VIF: regress each candidate feature on every other candidate feature and read off R². This is mathematically identical to `car::vif()` for a model with only continuous predictors (which is all this step ever needed), and avoids `car`'s heavy, R-version-sensitive dependency chain entirely. Computed on a capped subsample purely to keep each iteration's `lm()` call cheap -- VIF is a property of the predictor correlation structure, not something that needs the full 890k rows to estimate stably.

```{r manual-vif-function}
manual_vif <- function(data, features) {
  sapply(features, function(f) {
    others <- setdiff(features, f)
    if (length(others) == 0) return(1)
    probe <- lm(as.formula(paste(f, "~", paste(others, collapse = " + "))), data = data)
    r2 <- summary(probe)$r.squared
    # r2 essentially 1 means f is an exact (or near-exact) linear combination
    # of the others -- e.g. product_customer_risk_gap vs.
    # productReturnRate/customerReturnRate. VIF = Inf is the correct,
    # expected signal here; the loop below removes it first automatically.
    if (r2 >= 0.999999) return(Inf)
    1 / (1 - r2)
  })
}
```
